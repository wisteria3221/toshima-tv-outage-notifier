# verify-push

push 後の確認を同梱の `scripts/verify_push.py` に任せる。`gh run list` などを手で組み立てない。手で組み立てると、ランの取り違えや待機条件の誤りが起きやすい（下の「よくある誤り」）。

## 実行

```bash
python3 .claude/skills/verify-push/scripts/verify_push.py [--sha <commit>]
```

- **Bash の `run_in_background: true` で実行する**。障害チェックは cron-job.org から 10 分ごと（毎時 :07, :17, …, :57）に起動するので、完了まで最大 25 分ほど待つ。フォアグラウンドで実行すると Bash のタイムアウト（最大 10 分）で切れる。完了すると通知が来るので、それまで出力をポーリングしない
- `--sha` の既定はローカルの HEAD。PR をマージした後は `git pull` してから実行するか、マージコミットを `--sha` で指定する
- 待たずに CI だけを見たいときは `--skip-outage` を付ける。その他のオプションは `--help` で確認する

## 報告

スクリプトの標準出力（Markdown の表と詳細）をそのまま報告する。終了コードによって次のように扱う。

| 終了コード | 意味 | 対応 |
|---|---|---|
| 0 | すべて正常（障害チェックの終了コード 2 = 上流不通も含む） | 表をそのまま報告する。終了コード 2 なら「としまテレビ側に届かなかった。次回再試行される」と添える |
| 1 | CI 失敗・障害チェック失敗・state の push 失敗・Healthchecks 送信失敗のいずれか | 失敗した項目の `gh run view <id> --log-failed` を読み、原因を報告する。state の push 失敗は次回二重投稿の恐れがあるので最優先で伝える |
| 3 | 待ち時間内にランが見つからない・終わらない | cron-job.org が止まっている可能性がある。`cron-job-org-api` スキルでジョブの実行履歴を確認する |

「障害チェック: 対象外」と出たら、そのコミットはまだ `main` に入っていない（ブランチへの push）。マージ後に `--sha <マージコミット>` で実行し直す。

## よくある誤り（スクリプトが防いでいるもの）

- **日付でランを絞り込む**: ローカル日付（JST）と GitHub の `createdAt`（UTC）は日付がずれる。スクリプトは「push 時刻以降に作られ、対象コミットを含む」ランを探す
- **`headSha == sha` だけで照合する**: 実行中だったランが push の後に state を自動コミットすると、次のランの headSha は対象コミットより後のコミットになる。スクリプトは GitHub の compare API で「対象コミットを含むか」を判定する
- **`gh run list -L 30` の窓の端を初回とみなす**: 時間が経つと push 後初回のランが窓から外れる。スクリプトは push 時刻より前のランが入るまで窓を広げる
- **ログの `push が拒否されたため…` を実際の出力とみなす**: スクリプト本文のエコー（色コード `[36;1m` 付きの行）にも同じ文字列がある
