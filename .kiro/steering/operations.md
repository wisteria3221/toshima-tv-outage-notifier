# 運用標準

[目的: 無人で動き続ける通知バッチを「止まっていることに気づける」状態に保つ。設計上の理由は tech.md の「重要な技術的判断」に、ここには運用の手順と判断基準を書く]

## 基本方針

- 本番環境は GitHub Actions のみ。ステージングは持たず、ローカルの `DRY_RUN=true` 実行が代わり
- 「失敗を見逃す」ことを最大のリスクとして扱う。失敗は必ずジョブ失敗かアラートのどちらかに表れるようにする
- 復旧は fix-forward ではなく「状態をコミットしない → 次回実行が自然に再試行する」仕組みに頼る。手動で状態を直すのは最後の手段

## 起動経路と監視

```
cron-job.org ──workflow_dispatch──┐
                                  ├─▶ check-outage.yml ──ping──▶ Healthchecks.io ──▶ 通知先
GitHub schedule（フォールバック）──┘        │
                                            └─ exit 0 のときだけ data/state.json をコミット
```

| 経路 | 役割 | 止まったときの見え方 |
|---|---|---|
| 外部 cron（毎時 7, 37 分） | 主系。GitHub の Fine-grained PAT で dispatch | 起動回数が `schedule` 分だけに落ちる → Healthchecks の期限切れで検知 |
| `schedule`（毎時 22, 52 分） | フォールバック。GitHub 側で間引かれる前提 | 単独では検知不能。履歴に残らない |
| Healthchecks.io | dead-man's switch。Period 30 分 / Grace 1 時間 | ping 途絶で通知先にアラート |

- `concurrency: group: check-outage` で直列化しているため、2 経路が重なっても state.json の push は衝突しない。「待機中のラン」が見えるのは正常
- Healthchecks 未設定（`HEALTHCHECKS_URL` 空）の構成は許容するが、その場合は未起動を検知できないことを理解した上で運用する

## 実行結果の読み方と対処

終了コードはプロセスとワークフローの契約（tech.md 参照）。Actions の表示から対処を決める。

| 見え方 | 意味 | 対処 |
|---|---|---|
| 緑 | 成功。変更があれば state.json がコミットされる | なし |
| 緑 + 警告アノテーション「Upstream unavailable」 | 終了コード 2。としまテレビ側に到達できない | 単発なら放置。Healthchecks の `/log` に記録される。数時間続く場合は実際にサイトが落ちているかブラウザで確認 |
| 赤（Run outage checker で失敗） | 終了コード 1。通知失敗・0 件解析・予期しない例外 | ログで原因を分類（下表）。状態はコミットされていないので、原因を直せば次回実行で再通知される |
| 赤（Lint / Run tests で失敗） | コード品質ゲートで止まった。障害チェック自体が走っていない | 直ちに修正して push。この間は通知が完全に止まる |
| Healthchecks からアラート | 一定時間 ping がない | Actions の履歴を確認。ランが無い → 外部 cron のトークン期限切れや cron-job.org 側の停止を疑う。ランはあるが全部 2 → 上流不通の長期化 |

終了コード 1 の原因分類:

- **`ツイート投稿に失敗`**: X API 側。`402 Payment Required` はクレジット切れ、`401/403` はトークン失効や権限不足（Read and Write が必要）。Developer Portal で確認し、必要ならシークレットを更新
- **`X API認証情報が設定されていません`**: シークレット未設定。4 つすべてが揃っているか確認
- **`障害情報を取得できませんでした（ページ構造が変わった可能性）`**: ページは取れたが 1 件も解析できない。実際のページを見て `tests/fixtures/trouble_list.html` を更新し、スクレイパーの正規表現を追従させる
- **`予期しないエラー`**: スタックトレースを見てバグとして扱う

## 状態ファイル（data/state.json）の扱い

状態ファイルは通知判断の唯一の根拠。壊すと二重通知か欠落通知のどちらかが起きる。

- **手動編集しない**。例外は「意図的な初期化」のみで、その場合は `outages` を空にしてコミットする。掲載中の障害がすべて新規として通知されることを受け入れる
- **ローカルで実行したら戻す**。`DRY_RUN=true` でも通知済みマークとカウンタ加算が書き込まれる。`git checkout data/state.json` で戻してからコミットする
- **Actions のコミットは `[skip ci]` 付き**。これにより Lint ワークフローが状態コミットで走らない。手動で状態をコミットするときも同じ流儀に揃える
- **通知失敗時はコミットされない**のが仕様。「赤いランの後に state.json が更新されていない」は正常で、手で補完しない
- スキーマ変更時は `StateManager.SCHEMA_VERSION` を上げ、旧形式を読んだときの扱い（そのまま読む／初期化する）を `_load_state()` で明示する

## レート制限時の挙動

X API Free 枠（月 500）に対し 450 を上限とし、月初（UTC）にリセットされる。

- 405 件（90%）以上: 新規障害のみ通知。ステータス変更は「スキップ」で、失敗ではない
- 450 件到達: 以後通知しない。検出した変更は状態に保存されるので、翌月に遡って通知されることはない
- 実績は月 0〜15 件（2025-12〜2026-10、直近半年は 1〜7 件）。カウンタが急増していたら、スクレイパーが同じ障害を別 ID として検出している可能性を疑う

## シークレットとローテーション

| 項目 | 保管場所 | 期限・更新 |
|---|---|---|
| X API の 4 トークン | リポジトリのシークレット | 失効しないが、課金状態や権限変更で使えなくなる。失敗時は Developer Portal を確認 |
| GitHub Fine-grained PAT（dispatch 用） | cron-job.org のヘッダ | **有効期限あり**。期限切れは Healthchecks 経由でしか気づけないので、期限より前にカレンダー等で更新を予定する。権限は対象リポジトリの `Actions: Read and write` のみ |
| Healthchecks の Ping URL | リポジトリのシークレット | 期限なし。URL 自体が認証情報なのでログや Issue に貼らない |

- シークレットの値はリポジトリ・Issue・PR・ログに一切書かない。ログに出すのは「設定されているか」の真偽だけ
- `.env` は Git 管理外。`.env.example` にはプレースホルダのみ置く

## 変更をデプロイするときのチェックリスト

デプロイは `main` への push と同義。専用のリリース手順はない。

1. `uv run ruff check --fix . && uv run ruff format .` と `uv run pytest` をローカルで通す（CI の Lint 失敗は通知停止に直結する）
2. 依存を変えたら `uv lock` を実行し `uv.lock` もコミットする（CI は `--frozen`）
3. `DRY_RUN=true uv run python -m src.main` で本物のページに対して動作確認し、その後 `data/state.json` を戻す
4. 終了コードの意味や Healthchecks の送り分けを変えるときは、`src/main.py`・`check-outage.yml`・README の 3 箇所を同時に更新する
5. push 後、次の実行（最長 30 分以内）が緑になることを Actions で確認する

ロールバックは `git revert` で十分。状態ファイルはコードと独立しているため、コードを戻しても通知履歴は壊れない。
