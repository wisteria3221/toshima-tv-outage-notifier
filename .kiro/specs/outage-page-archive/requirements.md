# Requirements Document

## Project Description (Input)
障害の新規検出時とステータス変更の検出時に、その障害の詳細ページ（通知本文の「詳細:」に載せる URL）の魚拓（ウェブアーカイブ）を取得し、魚拓の URL を通知には含めず、記録として `data/state.json` の該当障害エントリに残す。魚拓の取得はベストエフォートとし、失敗しても通知・状態保存・終了コードには影響させない。

## Introduction

としまテレビ障害通知システムは、障害情報一覧ページから障害を検出して X へ通知するが、通知本文に載せる詳細ページは公式サイト側で後から書き換えられたり削除されたりする可能性がある。運用者は、通知した時点の詳細ページの内容を第三者のウェブアーカイブ（魚拓）として残し、その URL を記録として保持したい。

本機能は、新規障害の検出時と各ステータス変更の検出時に詳細ページの魚拓を取得し、その公開 URL を状態ファイルの該当障害エントリに追記する。魚拓の URL は通知本文に含めない。取得は通知の後に行うベストエフォートの処理であり、失敗しても通知の成否・通知済みマーク・月間カウンタ・終了コードを変えない。

## Boundary Context

- **In scope**:
  - 新規障害の検出時、および各ステータス変更の検出時に、詳細ページ（`/trouble/detail/<ID>`）の魚拓を外部のウェブアーカイブサービスで取得する
  - 取得した魚拓の公開 URL を、対象ステータス・取得日時とともに状態ファイルの該当障害エントリに記録する
  - 認証情報の設定方法と無効化（未設定時・DRY RUN 時）の挙動
  - 運用ドキュメント（README、環境変数テンプレート、ワークフローのシークレット設定）の更新
- **Out of scope**:
  - 魚拓 URL を通知本文（ツイート）に含めること
  - 障害情報一覧ページ（`/trouble/`）の魚拓
  - 本機能導入前に検出済みの障害に対する遡っての魚拓取得
  - 失敗した魚拓取得を以降の実行で再試行すること
  - ウェブアーカイブサービスの障害や制限に対する補償（別サービスへのフォールバック、自前での HTML 保存）
- **Adjacent expectations**:
  - 通知の判定・投稿・通知済みマーク・巻き戻し・状態保存の流れは現状のまま維持され、本機能はその後段に追加される
  - 状態ファイルの自動コミット（終了コード 0/1 のとき）と push 衝突時の JSON 検証は既存のワークフローがそのまま担う
  - 通知に失敗した障害は既存の巻き戻しにより状態に残らないため、その障害は次回実行で再検出される

## Requirements

### Requirement 1: 魚拓取得の契機と対象

**Objective:** 運用者として、障害を新規に検出したときと各ステータス変更を検出したときに、その障害の詳細ページの魚拓を取ってほしい。そうすれば、公式ページが後から書き換えられたり削除されたりしても、通知した時点の内容を参照できる。

#### Acceptance Criteria

1. When 新規障害を検出し、その通知処理が「送信」または「スキップ」で完了した, the 監視システム shall その障害の詳細ページの魚拓を取得する
2. When ステータス変更を検出し、その通知処理が「送信」または「スキップ」で完了した, the 監視システム shall その障害の詳細ページの魚拓を改めて取得する（変更後のステータスに対応する 1 件として扱う）
3. While 月間投稿制限により通知がスキップされている, the 監視システム shall 魚拓の取得を通常どおり行う
4. If ある変更の通知が「失敗」した, then the 監視システム shall その変更については魚拓を取得しない（巻き戻し後、次回実行で再検出されたときに取得する）
5. When 1 回の実行で複数の変更を検出した, the 監視システム shall すべての通知処理を終えてから魚拓の取得を開始する
6. The 監視システム shall 魚拓の対象を詳細ページの URL（通知本文の「詳細:」行に載せる URL と同一）に限定し、一覧ページは対象にしない

### Requirement 2: 魚拓の記録

**Objective:** 運用者として、取得した魚拓の URL を障害ごとの記録として状態ファイルに残してほしい。そうすれば、通知には含めずに、後から障害ごと・ステータスごとに魚拓を参照できる。

#### Acceptance Criteria

1. When 魚拓の取得に成功した, the 監視システム shall 対象障害の状態エントリに「対象ステータス」「取得日時（UTC）」「魚拓の公開 URL」からなる記録を 1 件追加する
2. The 監視システム shall 同じ障害の既存の魚拓記録を保持したまま追記する（過去のステータスの記録を上書き・削除しない）
3. The 監視システム shall 魚拓の記録を状態ファイルに保存し、既存の状態ファイル自動コミットの仕組みでリポジトリに残す
4. The 監視システム shall 魚拓の URL を通知本文に含めない
5. When 魚拓の記録を持たない既存の状態ファイル（旧スキーマ）を読み込む, the 監視システム shall 変換作業なしでそのまま読み込み、記録なしとして扱う
6. When 既存障害の情報（タイトル・ステータス等）を更新する, the 監視システム shall その障害の魚拓記録を保持する

### Requirement 3: ベストエフォート（失敗の隔離）

**Objective:** 運用者として、魚拓の取得が失敗しても通知の仕組みに影響を与えないでほしい。そうすれば、外部アーカイブサービスの不調で障害の速報が止まったり、ジョブが失敗扱いになって本来の失敗が埋もれたりしない。

#### Acceptance Criteria

1. If 魚拓の取得が失敗した（アーカイブサービスのエラー応答、通信エラー、時間切れ）, then the 監視システム shall 原因を含む警告ログを出し、記録を追加せずに処理を続行する
2. The 監視システム shall 魚拓の取得結果によって通知の成否判定・通知済みマーク・月間カウンタ・終了コードを変えない
3. The 監視システム shall 魚拓 1 件の取得に費やす時間に上限を設け、上限を超えた場合は失敗として扱う
4. The 監視システム shall 失敗した魚拓の取得を以降の実行で再試行しない
5. If 魚拓の取得処理で予期しない例外が発生した, then the 監視システム shall 例外をログに記録して処理を続行し、状態保存と終了コードに影響させない
6. When 魚拓の取得を 1 件以上試みた, the 監視システム shall 実行の最後に取得成功件数と失敗件数をログに出す

### Requirement 4: 設定と無効化

**Objective:** 運用者として、アーカイブサービスの認証情報を既存のシークレットと同じ方法で設定し、未設定時や動作確認時には魚拓の取得を安全に止められるようにしてほしい。そうすれば、認証情報を漏らさずに運用でき、ローカルの動作確認で本物の魚拓を作ってしまうこともない。

#### Acceptance Criteria

1. The 監視システム shall アーカイブサービスの認証情報を環境変数（ローカルでは `.env`、GitHub Actions ではリポジトリのシークレット）から読み込む
2. If 認証情報が設定されていない, then the 監視システム shall 魚拓の取得を行わず、魚拓の対象がある実行で警告ログを 1 回出す
3. While DRY RUN モードが有効, the 監視システム shall アーカイブサービスへ保存要求を送らず、対象 URL をログに出す
4. The 監視システム shall 認証情報の値をログ・通知本文・状態ファイルに出力しない

### Requirement 5: ドキュメントと品質ゲート

**Objective:** 運用者および保守開発者として、認証情報の取得・設定手順と記録の場所が文書化され、既存の品質基準が維持されてほしい。そうすれば、設定漏れなく導入でき、CI の Lint・テストが壊れて障害チェックに影響することもない。

#### Acceptance Criteria

1. The README shall 認証情報の取得方法、ローカルと GitHub Actions での設定手順、魚拓の記録場所と形式を説明する
2. The 環境変数テンプレート（`.env.example`）とワークフロー定義 shall 新しい認証情報の項目を含む
3. The 運用ドキュメント（steering の運用標準） shall シークレット一覧に魚拓用の認証情報を追加する
4. When 変更後にテストスイートと Ruff（check / format）を実行する, the コードベース shall 全テストを通過させ、リント・フォーマット違反を発生させない
